   189→S2-T3 — S2-T3 — ShiftService — Shift Lifecycle & Remittance Business Logic
   190→ID: 86d3c0xb1 | status: complete
   191→--------------------------------------------------------------------------------
   192→Implement the core business logic for the conductor shift lifecycle including shift start (with vehicle + driver selection), shift end (via remittance submission), and shift history.
   193→
   194→## Context
   195→
   196→The shift flow is:
   197→1. Conductor logs in
   198→2. Conductor selects which vehicle/unit they are operating AND which driver they are paired with
   199→3. Shift starts — conductor + driver + vehicle are linked
   200→4. During shift: GPS tracking + fare transactions happen
   201→5. Conductor submits remittance (total collected amount) → shift ends
   202→
   203→NO remittance = shift stays active. The shift ends ONLY upon remittance submission.
   204→
   205→This pairing matters because later:
   206→- Payments → which conductor+driver handled this fare?
   207→- Feedback → commuter rates a ride → which shift? which conductor? which driver?
   208→- Disputes → who was responsible for this trip?
   209→
   210→## ShiftService Methods
   211→
   212→Create app/Services/ShiftService.php:
   213→
   214→### startShift(User $conductor, string $vehicleId, string $driverId): ShiftLog
   215→- Validate conductor role is CONDUCTOR
   216→- Check conductor has no existing active shift → if yes, throw 409 Conflict
   217→- Check driver is not already on another active shift → if yes, throw 409 Conflict
   218→- Check vehicle is not already on another active shift → if yes, throw 409 Conflict
   219→- Create ShiftLog record: conductor_id, driver_id, vehicle_id, status=ACTIVE, started_at=now()
   220→- Update vehicle.active_shift_id = new shift ID
   221→- Update driver.active_shift_id = new shift ID
   222→- Return the ShiftLog
   223→
   224→### endShiftViaRemittance(User $conductor, string $shiftId, float $totalCollected, float $remittedAmount): ShiftLog
   225→- Validate the shift belongs to this conductor → if not, 403
   226→- Validate shift status is ACTIVE → if not, 422
   227→- Create Remittance record: shift_id, conductor_id, driver_id, vehicle_id, total_collected, remitted_amount
   228→- Update ShiftLog: status=ENDED, ended_at=now()
   229→- Clear vehicle.active_shift_id = null
   230→- Clear driver.active_shift_id = null
   231→- Return the ShiftLog
   232→
   233→### getActiveShift(User $conductor): ?ShiftLog
   234→- Return the conductor's current active shift (status=ACTIVE, scoped to auth conductor)
   235→- Return null if no active shift
   236→- Eager load: vehicle, driver, route relationships
   237→
   238→### getShiftLogs(User $conductor, int $perPage = 15): LengthAwarePaginator
   239→- Return paginated shift history for the authenticated conductor
   240→- Order by started_at DESC
   241→- Eager load: vehicle, driver, route
   242→
   243→### getShiftDetail(User $conductor, string $shiftId): ShiftLog
   244→- Return a single shift with all relationships
   245→- Validate shift belongs to this conductor
   246→- Eager load: vehicle, driver, route, remittance, transactions
   247→
   248→## Error Responses
   249→
   250→All methods must use the ApiResponse trait format:
   251→- 409 Conflict: { success: false, message: 'Already on active shift' } (duplicate shift)
   252→- 409 Conflict: { success: false, message: 'Driver already on active shift' }
   253→- 409 Conflict: { success: false, message: 'Vehicle already on active shift' }
   254→- 403 Forbidden: { success: false, message: 'Forbidden' }
   255→- 422 Validation: { success: false, message: 'Validation failed', errors: {...} }
   256→
   257→Acceptance Criteria
   258→ Conductor can only have ONE active shift (409 on duplicate)
   259→ Driver can only be on ONE active shift (409 on duplicate)
   260→ Vehicle can only have ONE active shift (409 on duplicate)
   261→ Shift ends ONLY via remittance submission — no standalone end-shift endpoint
   262→ vehicle.active_shift_id is set on shift start, cleared on shift end
   263→ driver.active_shift_id is set on shift start, cleared on shift end
   264→ Remittance record is created when shift ends
   265→ All error responses use ApiResponse format
   266→ No business logic in controllers — all logic in ShiftService

   271→S2-T4 — S2-T4 — LocationService — GPS Tracking, Vehicle Location Logic & Real-Time Broadcasting
   272→ID: 86d3c0xbe | status: complete
   273→--------------------------------------------------------------------------------
   274→Implement the GPS tracking service for real-time vehicle location updates and commuter-facing vehicle location queries. GPS updates trigger Pusher broadcast events so commuters see location changes in real-time via Laravel Echo.
   275→
   276→## Context
   277→
   278→During an active shift, conductors send GPS updates every ~5 seconds. These updates are stored via upsert in vehicle_locations (always latest position only). Each update also broadcasts a VehicleLocationUpdated event via Pusher so subscribed commuters receive the new position instantly. The GET /api/vehicles/locations endpoint remains as a fallback for initial load and reconnection.
   279→
   280→## LocationService Methods
   281→
   282→Create app/Services/LocationService.php:
   283→
   284→### updateLocation(User $conductor, float $lat, float $lng, ?float $speed = null, ?float $heading = null, ?string $capacityStatus = null): VehicleLocation
   285→- Validate lat range: -90 to 90 → if out of range, 422
   286→- Validate lng range: -180 to 180 → if out of range, 422
   287→- Get the conductor's active shift → if no active shift, 422 ('No active shift')
   288→- Get the vehicle_id from the active shift
   289→- Upsert vehicle_locations by vehicle_id:
   290→  - UPDATE if vehicle_id exists: lat, lng, speed, heading, capacity_status, conductor_id, updated_at
   291→  - INSERT if vehicle_id does not exist
   292→- Broadcast VehicleLocationUpdated event with the updated vehicle location data
   293→- Return the VehicleLocation
   294→
   295→### getAllActiveLocations(): Collection
   296→- Return all vehicles from vehicle_locations table
   297→- No distance filter — ALL vehicles are visible to commuters at ALL times
   298→- Join with vehicles table to include: plate_number, vehicle_type
   299→- Join with active shifts to include: route info
   300→- Each record should return: vehicle_id, plate_number, vehicle_type, lat, lng, speed, heading, capacity_status, route_name, updated_at
   301→- Order by updated_at DESC (most recently updated first)
   302→- NOTE: This endpoint serves as fallback/initial load. Real-time updates come via Pusher broadcast.
   303→
   304→### updateCapacityStatus(User $conductor, string $status): VehicleLocation
   305→- Validate status is one of: AVAILABLE, STANDING, FULL
   306→- Get the conductor's active shift → if no active shift, 422
   307→- Get the vehicle_id from the active shift
   308→- Upsert vehicle_locations with new capacity_status
   309→- Broadcast VehicleLocationUpdated event with updated capacity status
   310→- Return the updated VehicleLocation
   311→
   312→## Broadcasting Integration
   313→
   314→When a GPS update or capacity status change occurs:
   315→- Broadcast VehicleLocationUpdated event on the 'vehicles' Pusher channel
   316→- Event payload includes: vehicle_id, plate_number, lat, lng, speed, heading, capacity_status, route_name, updated_at
   317→- Commuter frontend subscribes to 'vehicles' channel via Laravel Echo to receive real-time updates
   318→- GET /api/vehicles/locations is the fallback for initial page load and reconnection
   319→
   320→## Capacity Status Rules
   321→
   322→- AVAILABLE → vehicle has seats
   323→- STANDING → vehicle is standing room only
   324→- FULL → vehicle cannot take more passengers
   325→- Capacity status is conductor-updated only — the frontend NEVER infers or sets this
   326→- This is server-authoritative data
   327→
   328→## Hard Constraints
   329→
   330→- NO distance filter on getAllActiveLocations — visibility is unrestricted
   331→- NO radius/radius logic in this service — that belongs to HailService (Sprint 3)
   332→- Upsert pattern is mandatory — never append-only
   333→- GPS updates require an active shift — no shift = no location update
   334→- Every GPS update MUST broadcast via Pusher (no silent updates)
   335→
   336→Acceptance Criteria
   337→ GPS POST updates vehicle_locations via upsert (always latest position)
   338→ GPS updates trigger VehicleLocationUpdated broadcast event
   339→ getAllActiveLocations returns ALL vehicles with no distance filter
   340→ Invalid lat/lng values return 422 validation error
   341→ GPS update without an active shift returns 422
   342→ Capacity status can only be updated by conductor with active shift
   343→ Capacity status updates trigger VehicleLocationUpdated broadcast event
   344→ Capacity status values are restricted to AVAILABLE, STANDING, FULL
   345→ No duplicate vehicle records in vehicle_locations (upsert enforced)
   346→ All responses use ApiResponse format
   347→ No business logic in controllers — all logic in LocationService
   348→Post-Task Requirement
