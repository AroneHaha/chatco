   186→===== TASK 86d3c0xb1 =====
   187→NAME: S2-T3 — ShiftService — Shift Lifecycle & Remittance Business Logic
   188→---DESCRIPTION---
   189→Implement the core business logic for the conductor shift lifecycle including shift start (with vehicle + driver selection), shift end (via remittance submission), and shift history.
   190→
   191→## Context
   192→
   193→The shift flow is:
   194→1. Conductor logs in
   195→2. Conductor selects which vehicle/unit they are operating AND which driver they are paired with
   196→3. Shift starts — conductor + driver + vehicle are linked
   197→4. During shift: GPS tracking + fare transactions happen
   198→5. Conductor submits remittance (total collected amount) → shift ends
   199→
   200→NO remittance = shift stays active. The shift ends ONLY upon remittance submission.
   201→
   202→This pairing matters because later:
   203→- Payments → which conductor+driver handled this fare?
   204→- Feedback → commuter rates a ride → which shift? which conductor? which driver?
   205→- Disputes → who was responsible for this trip?
   206→
   207→## ShiftService Methods
   208→
   209→Create app/Services/ShiftService.php:
   210→
   211→### startShift(User $conductor, string $vehicleId, string $driverId): ShiftLog
   212→- Validate conductor role is CONDUCTOR
   213→- Check conductor has no existing active shift → if yes, throw 409 Conflict
   214→- Check driver is not already on another active shift → if yes, throw 409 Conflict
   215→- Check vehicle is not already on another active shift → if yes, throw 409 Conflict
   216→- Create ShiftLog record: conductor_id, driver_id, vehicle_id, status=ACTIVE, started_at=now()
   217→- Update vehicle.active_shift_id = new shift ID
   218→- Update driver.active_shift_id = new shift ID
   219→- Return the ShiftLog
   220→
   221→### endShiftViaRemittance(User $conductor, string $shiftId, float $totalCollected, float $remittedAmount): ShiftLog
   222→- Validate the shift belongs to this conductor → if not, 403
   223→- Validate shift status is ACTIVE → if not, 422
   224→- Create Remittance record: shift_id, conductor_id, driver_id, vehicle_id, total_collected, remitted_amount
   225→- Update ShiftLog: status=ENDED, ended_at=now()
   226→- Clear vehicle.active_shift_id = null
   227→- Clear driver.active_shift_id = null
   228→- Return the ShiftLog
   229→
   230→### getActiveShift(User $conductor): ?ShiftLog
   231→- Return the conductor's current active shift (status=ACTIVE, scoped to auth conductor)
   232→- Return null if no active shift
   233→- Eager load: vehicle, driver, route relationships
   234→
   235→### getShiftLogs(User $conductor, int $perPage = 15): LengthAwarePaginator
   236→- Return paginated shift history for the authenticated conductor
   237→- Order by started_at DESC
   238→- Eager load: vehicle, driver, route

   240→### getShiftDetail(User $conductor, string $shiftId): ShiftLog

   271→
   272→## Context
   273→
   274→During an active shift, conductors send GPS updates every ~5 seconds. These updates are stored via upsert in vehicle_locations (always latest position only). The GET /api/vehicles/locations endpoint remains as a fallback for initial load and reconnection.
   275→
   276→## LocationService Methods
   277→
   278→Create app/Services/LocationService.php:
   279→
   280→### updateLocation(User $conductor, float $lat, float $lng, ?float $speed = null, ?float $heading = null, ?string $capacityStatus = null): VehicleLocation
   281→- Validate lat range: -90 to 90 → if out of range, 422
   282→- Validate lng range: -180 to 180 → if out of range, 422
   283→- Get the conductor's active shift → if no active shift, 422 ('No active shift')
   284→- Get the vehicle_id from the active shift
   285→- Upsert vehicle_locations by vehicle_id:
   286→  - UPDATE if vehicle_id exists: lat, lng, speed, heading, capacity_status, conductor_id, updated_at
   287→  - INSERT if vehicle_id does not exist
   288→- Broadcast VehicleLocationUpdated event with the updated vehicle location data
   289→- Return the VehicleLocation
   290→
   291→### getAllActiveLocations(): Collection
   292→- Return all vehicles from vehicle_locations table
   293→- No distance filter — ALL vehicles are visible to commuters at ALL times
   294→- Join with vehicles table to include: plate_number, vehicle_type
   295→- Join with active shifts to include: route info
   296→- Each record should return: vehicle_id, plate_number, vehicle_type, lat, lng, speed, heading, capacity_status, route_name, updated_at
   297→- Order by updated_at DESC (most recently updated first)
   298→- NOTE: This endpoint serves as fallback/initial load. Real-time updates come via Pusher broadcast.
   299→
   300→### updateCapacityStatus(User $conductor, string $status): VehicleLocation
   301→- Validate status is one of: AVAILABLE, STANDING, FULL
   302→- Get the conductor's active shift → if no active shift, 422
   303→- Get the vehicle_id from the active shift
   304→- Upsert vehicle_locations with new capacity_status
   305→- Broadcast VehicleLocationUpdated event with updated capacity status
   306→- Return the updated VehicleLocation
   307→
   308→## Broadcasting Integration
   309→
   310→When a GPS update or capacity status change occurs:
   311→- Broadcast VehicleLocationUpdated event on the 'vehicles' Pusher channel
   312→- Event payload includes: vehicle_id, plate_number, lat, lng, speed, heading, capacity_status, route_name, updated_at
   313→- Commuter frontend subscribes to 'vehicles' channel via Laravel Echo to receive real-time updates
   314→- GET /api/vehicles/locations is the fallback for initial page load and reconnection
   315→

   317→
   318→- AVAILABLE → vehicle has seats
   319→- STANDING → vehicle is standing room only
   320→- FULL → vehicle cannot take more passengers
   321→- Capacity status is conductor-updated only — the frontend NEVER infers or sets this

   328→- Upsert pattern is mandatory — never append-only

   339→ Capacity status updates trigger VehicleLocationUpdated broadcast event
